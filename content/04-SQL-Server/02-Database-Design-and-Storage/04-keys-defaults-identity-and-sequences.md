# Keys, Defaults, Identity, and Sequences

This note owns the row-identity and value-generation choices that sit underneath table design: natural keys, surrogate keys, `IDENTITY`, `SEQUENCE`, and default constraints.

## Natural Keys, Surrogate Keys, and Composite Keys

### Natural keys

Use a natural key when the source attribute is:

- truly stable
- already enforced by the business domain
- small enough to be practical in joins and indexes

### Surrogate keys

Use a surrogate key when:

- the business key is wide or volatile
- the source key changes over time
- you need a compact clustering or foreign-key surface
- slowly changing dimensions require one business entity to have multiple row versions

### Composite keys

Composite keys are often the correct choice for fact-like tables and time-series data. Avoid adding a surrogate key purely out of habit when the real row identity is already a small, stable combination such as `(instrument_id, price_date)`.

## IDENTITY Behavior and Retrieval Patterns

### What `IDENTITY` gives you and what it does not

`IDENTITY` gives you an automatically generated numeric value. It does **not** guarantee:

- gap-free numbering
- transaction rollback reuse
- business ordering correctness
- cross-table coordination

*This example creates a surrogate-key identity column and leaves business uniqueness to a separate constraint.*

```sql
CREATE TABLE silver.instrument_dim
(
    instrument_id   int IDENTITY(1,1) NOT NULL,
    symbol          varchar(32)       NOT NULL,
    valid_from      datetime2(3)      NOT NULL,
    valid_to        datetime2(3)      NOT NULL,
    is_current      bit               NOT NULL,
    CONSTRAINT PK_instrument_dim PRIMARY KEY CLUSTERED (instrument_id),
    CONSTRAINT UQ_instrument_dim_symbol_valid_from UNIQUE (symbol, valid_from)
);
```

### Retrieve the generated value correctly

Use:

- `SCOPE_IDENTITY()` for the last identity value generated in the current scope
- `OUTPUT INSERTED.<column>` when inserting multiple rows or when you need a safer, set-based capture pattern

Avoid `@@IDENTITY` for application logic because triggers can make it return a value from a different scope.

## SEQUENCE Objects

### When `SEQUENCE` is better than `IDENTITY`

Use `SEQUENCE` when you need:

- reusable number generation across multiple tables
- explicit control of `CACHE`, `MINVALUE`, `MAXVALUE`, or cycling
- a value before the insert statement executes

*This example creates a reusable sequence for a control table or multi-table identifier space.*

```sql
CREATE SEQUENCE control.pipeline_run_id_seq
    AS bigint
    START WITH 1
    INCREMENT BY 1
    CACHE 100;
```

*This example consumes the sequence explicitly in an insert statement.*

```sql
INSERT INTO control.pipeline_run
(
    pipeline_run_id,
    pipeline_name,
    started_at_utc
)
VALUES
(
    NEXT VALUE FOR control.pipeline_run_id_seq,
    'daily_stoxx_pipeline',
    SYSUTCDATETIME()
);
```

## Default Constraints and Generated Values

### Default constraints

Use default constraints for values that are truly generated by the database contract, such as:

- `SYSUTCDATETIME()` for created timestamps
- `NEWID()` or `NEWSEQUENTIALID()` for GUID-based identifiers
- fixed status values that the application may omit on insert

Do not use defaults to hide missing business inputs that the caller should have provided explicitly.

### `NEWID()` vs `NEWSEQUENTIALID()`

- `NEWID()` is globally unique but random and fragmentation-heavy when used in clustered keys
- `NEWSEQUENTIALID()` is still unique but far friendlier to clustered insert locality

### `rowversion` is not a datetime

`rowversion` is useful as a change token, not as a business time or event-order truth source across systems. Use it for optimistic concurrency or incremental detection, not for temporal meaning.

## Practical Selection Rules

1. use a natural key only when it is small, stable, and business-authoritative
2. use a surrogate key when versioning, volatility, or width make the natural key awkward
3. use a composite key when the row identity is already naturally composite and operationally stable
4. use `IDENTITY` for simple single-table surrogates
5. use `SEQUENCE` when the number generator must outlive one table
6. use defaults only for contract-owned generated values
